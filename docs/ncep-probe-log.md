# NCEP probe log (WiseCAM import)

Purpose: find out why WiseCAM imports its own `.ncep` exports but rejects the ones our writer
produces. Record every probe, what changed, and whether it imported. Keep the working/ failing
lists current — they are the reverse-engineering evidence.

Probe folders live in `~/Downloads/`:

- `ncep-probes-30-58/` — differential probes starting from WiseCAM's real `M-1.ncep`
- `ncep-probes-60-66/` — raw byte-preserving ZIP edits (container metadata untouched)
- `ncep-probes-70-83/` — our full package content + ZIP metadata isolation
- `ncep-probes-90-94/` — PFC variants: our package, and our part/adobe inside real packages
- `ncep-probes-100-124/` — fflate/zlib/timestamp/flag isolation (100–113) and PFC content in
  **unmodified real ZIP headers** (120–124)
- `ncep-probes-170-187/` — minimal diffs from real `M-8` (one ZIP field / one SVG element at a time)
- `ncep-probes-190-196/` — duplicate-mark / file-name cache test (unique marks `X-8` / `X-1`)
- `ncep-probes-200-207/` — technologyID cache proof (same file, only the GUID changed)
- `ncep-probes-220-229/` — compression-level isolation (220–225) and final level-6 packages (226–229)
- `ncep-probes-300-329/` — one-at-a-time content edits on real M-1 / M-26 / M-34
- `ncep-probes-400-531/` — section permutation matrix (same edits on PFC/UB/SHS/RHS)
- `ncep-probes-own/` — historical full own-part packages (240–245); **do not extend this route**
- `ncep-inject-620-627/` — control-first feature injection: own holes/end cut and donor bevels
- `ncep-export-variations/` — 19 real reference variants + `.ncexa`; canonical/mark/hole/bevel golden set (repo copy: `test/fixtures/ncep/reference-variations/`)

## Reference fixtures (do not delete)

`test/fixtures/ncep/` is the in-repo control group: **all 17 real exports** plus
`working/` (`30`, `30b`, `31`, `32`, `77`) and `manifest.json`. The real exports are the ZIP
dialect authority; `working/` are confirmed importable generated packages. A guard test
(`src/lib/wisecam/referenceFixtures.test.ts`) checks every SHA-256 and ZIP CRC, so deleting or
rewriting a reference fails the suite. Add a file only after it imports in WiseCAM, then
regenerate the manifest with the command in `test/fixtures/ncep/README.md`.

2. **fflate `zipSync` is accepted.** 30b (fflate level 6, real content) and 31/32 (same, GUID

## Real ZIP dialect (all 18 files in `NCEP samples 2 Hidden Grove`)

| Entry | Method | GP flags | internal_attr | version made by |
| --- | --- | --- | --- | --- |
| `mimetype` | store (0) | `0x0000` | 0 | 0 |
| `META-INF/container.xml` | **store (0)** | `0x0000` | 0 | 0 |
| `CAD/*` (xml/opf/svg) | deflate (8) | **`0x0006`** | **1** | 0 |
| `ncex.opf` | deflate (8) | `0x0000` | 1 | 0 |

- Entry order: `mimetype`, `META-INF/container.xml`, `CAD/CadRoot.xml`, `CAD/cad.opf`,
  `CAD/Technology.xml`, `CAD/CustomizeData.xml`, `CAD/adobe*.svg`, `CAD/part*.svg`, `ncex.opf`.
- `mimetype` is exactly `application/ncex+zip` (20 bytes, no newline).
- All timestamps are MS-DOS timestamps; mostly one timestamp per export (M-8 has two).
- No ZIP comment, no extra fields, no trailing bytes, no ZIP64, no signature files.
- XML/SVG use LF newlines, no BOM, no CRLF.
- CRC32 of every decompressed entry matches between the real package and the fflate rezip.

These traits match **Qt's `QZipWriter`** (version-made-by 0, flags `0x0006`, `internal_attr=1`).

## What fflate changes on re-zip

- Deflates `META-INF/container.xml` (the real package stores it).
- Writes GP flags `0x0000` instead of `0x0006` on CAD entries.
- Writes `internal_attr=0` instead of `1`.
- Writes version-made-by `20` instead of `0`.
- Rewrites all timestamps to the current time.

The rejection was too fast to be geometry validation; it was the ZIP metadata. Probe 77 showed
that the full Qt-style metadata set is accepted, so `zipQt` now emits all of it (the minimum
subset was never isolated, and does not need to be).

## Is the failure content size? (170–187)

`170` is a byte copy of the real `M-8.ncep`; `171` is a raw read/write of the same file (it is
**byte-identical** to 170, verified). `173` changes only the DOS timestamps. `172` changes only
the internal mark `M-8` → `X-8`. `174` recompresses one entry with identical bytes.

If **173** or **174** fails while 170 works, the failure is **not** "too big a content change":
even a timestamp or a re-compression is enough. That points at WiseCAM treating the file as a
different/new package, most likely a **duplicate part mark** (`M-8` already exists) or a cache,
rather than geometry.

Element swaps (real part + one of ours): `175` old text, `176` text content only, `177` section,
`178` holes, `179` truncate paths. `180` is our fixed whole part; `184`–`187` are our fixed part
with one real element put back. Use these to find a single offending element.

### Structural bug found: `cadgroup` was nested inside `cadpart`

Real parts (and the working 77 M-1) have the section group as a **sibling**:

```
<g cadpart> cuts/holes/text </g>
<g cadgroup> section </g>
```

Our `partSvg` originally emitted it **inside** `cadpart` (probe 77). It was later moved beside
`cadpart` (205/226). **The test result reverses the earlier conclusion:** 77 imports; 205/226 are
rejected. Real exports *do* put the group beside `cadpart`, but their group carries **two**
section paths (outer contour + inner contour); ours still has **one**. Moving the single-path
group out is the current regression — keep it nested, or emit the inner section path before
making it a sibling.

## Reject vs preview crash

WiseCAM fails in two distinct layers, and the layer tells us which part of the package is bad:

| Symptom | Layer | Typical cause |
| --- | --- | --- |
| **Rejected** (no preview, file refused) | ZIP/OPC container, `CadRoot.xml`, `ncex.opf` manifest | bad ZIP headers/CRC, unreadable XML, missing referenced file, unsupported profile |
| **Crashes on preview** | part/adobe SVG geometry renderer | malformed path, missing inner contour, notch/bevel the previewer can't build, bad `InnerCad` |

The 90–94 run already splits this way: `90-M-1` is **rejected**, while `M-8`/`M-34`/`M-40`
**crash on preview**. M-1 is also the case whose content works in real headers (77), so its
rejection is a container/ZIP difference; the others are more likely geometry.

Isolation matrix:

- `220` (our M-1, level 9) vs `221` (level 6) vs `224` (`zipSync` 6): if 220 is rejected and
  221/224 import, the level-9 deflate stream is the container-layer fault.
- `202` (real M-8 ZIP + our fixed part) vs `204` (our M-8 `zipQt`): if 202 crashes, our M-8
  geometry is the preview fault; if 202 imports, the fault is the container again.
- `227` (M-8 level 6) separates the two: if it imports, level was the only problem; if it still
  crashes, the M-8 geometry needs work.

Conclusions:

1. **PFC** is fine with exact outer vertices, including sharp chords (`1531`, `1403`).
2. **UB requires true arcs** for the root fillets; sharp root fails even with real trims/holes/marks
   (`1504`).
3. **Tubes require true arcs** for the corner radii; sharp outer is blocky/offset (`1530`).
4. **UB front trim/hole/mark is now solved**: real trims + holes + marks load (`1503`). The earlier
   front glitch was our front features, not the section alone.
5. **M-42 needs real mitred trims and the real section**: `1511`/`1513` load; our section with real
   trims still offsets the end cut (`1512`). The default mark is fine once the geometry is correct.
6. **Full packages still reject** (`1520–1526`) even when the part features are real. Since the same
   mixtures load in a **real container** (`806`, `808`, `809–811`), the remaining blocker is the
   package container/compression, not the NCEP geometry.
